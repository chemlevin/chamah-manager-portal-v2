# Table Blueprint — `daycares`

Status: Draft architecture based on approved concept.

Last updated: 2026-07-12

Related Handbook rules: BR-0047, BR-0065, BR-0159 through BR-0165.

Related decisions: DBD-0001 through DBD-0011; daycare represents one license; School-Year classroom structure is stored separately.

## Purpose

Store the stable identity of one licensed daycare. One Daycare equals one license. The table does not store annual classroom structure, monthly child counts, staffing requirements, tuition, or budget results.

## Source of Truth

- Operational editing interface: Google Sheets.
- Final system Source of Truth: Database after validation and synchronization.
- Website: future read consumer of accepted database data.

## Primary Key

- `daycare_id` — UUID, generated by the database, immutable.

## Business Code

- `daycare_code` — VARCHAR(50), required, unique, stable after use.

Examples are assigned during seed preparation. Display names must never be used as integration keys.

## Fields

| Field | Type | Nullable | Default | Notes |
|---|---|---:|---|---|
| `daycare_id` | UUID | No | generated | Stable internal identity |
| `daycare_code` | VARCHAR(50) | No | none | Stable Business Code |
| `display_name` | VARCHAR(150) | No | none | User-facing name |
| `license_number` | VARCHAR(100) | Yes | NULL | One daycare represents one license; exact requiredness depends on available source data |
| `legal_entity_id` | UUID | No | none | Current Legal Entity assignment for normal operation |
| `address_text` | VARCHAR(500) | Yes | NULL | Simple operational address; normalized address model is not required initially |
| `opened_on` | DATE | Yes | NULL | Operational opening date when known |
| `closed_on` | DATE | Yes | NULL | Operational closure date when applicable |
| `lifecycle_status` | VARCHAR(20) | No | `ACTIVE` | ACTIVE / INACTIVE / ARCHIVED |
| `display_order` | INTEGER | No | `0` | User-facing ordering |
| `created_at` | TIMESTAMPTZ | No | current timestamp | Audit metadata |
| `created_by_user_id` | UUID | Yes | NULL | Future user FK |
| `updated_at` | TIMESTAMPTZ | No | current timestamp | Audit metadata |
| `updated_by_user_id` | UUID | Yes | NULL | Future user FK |
| `row_version` | BIGINT | No | `1` | Concurrency protection for Sheet sync |

## Constraints

- Primary key on `daycare_id`.
- Unique `daycare_code`.
- `closed_on` must be null or on/after `opened_on`.
- A used Daycare is never physically deleted.
- `legal_entity_id` must reference an existing Legal Entity.
- Display-name changes do not change identity.
- A material business-meaning change requires a new Daycare and new Business Code.

License-number uniqueness is not imposed until the exact licensing format and reuse rules are confirmed. A Data Quality warning should identify duplicate active license numbers.

## Foreign Keys

- `legal_entity_id` -> `legal_entities.legal_entity_id`.
- Future audit user fields -> user/account table when designed.

## Indexes

- Unique index on `daycare_code`.
- Index on `legal_entity_id`.
- Index on `lifecycle_status`.
- Index on `(legal_entity_id, lifecycle_status)`.
- Optional index on `license_number` for duplicate review.

## Historical Behavior

The Daycare identity remains stable across School Years. Annual classroom composition, operating configuration, monthly enrollment, and budget data are stored in child tables.

If a Daycare moves to another Legal Entity, historical reporting must preserve the previous ownership. The detailed assignment-history table will be designed before implementation. The direct `legal_entity_id` field represents the current assignment and must not be used alone for historical reconstruction.

## Lifecycle

- `ACTIVE`: available for current operational configuration and new records.
- `INACTIVE`: not offered by default for new assignments; historical references remain valid.
- `ARCHIVED`: retained for history and excluded from normal operational lists.

Closure does not delete annual or monthly data.

## Effective Dates

Daycare identity is not recreated each School Year. Current lifecycle dates are represented by `opened_on` and `closed_on`. Legal Entity assignment history and School-Year operation are modeled separately.

## Relationships

- One Daycare has many Daycare School Year records.
- One Daycare has many legal-entity assignment-history records when a transfer occurs.
- One Daycare may have many Bank/Payroll/Budget allocations through operational records.
- One Daycare has many School-Year classrooms through `daycare_school_years`.

## Validation Rules

Blocking:

- Missing or duplicate Daycare Code.
- Missing Display Name.
- Invalid Legal Entity.
- Invalid lifecycle status.
- Closure date before opening date.
- Attempt to change an in-use Business Code.

Warnings:

- Missing license number.
- Duplicate active license number.
- Active Daycare with closure date in the past.
- Inactive Daycare without a closure date.

## Google Sheets Editing Model

Suggested spreadsheet: `Chamah - Organization & Daycares`.

Suggested tab: `DAYCARES`.

Editable columns:

- `daycare_code` only during new-record creation.
- `display_name`.
- `license_number`.
- `legal_entity` via dropdown.
- `address_text`.
- `opened_on`.
- `closed_on`.
- `lifecycle_status` via dropdown.
- `display_order`.

Protected columns:

- `database_id`.
- accepted Business Code after use.
- `row_version`.
- sync status and validation fields.
- audit timestamps and user IDs.

Free-text fields:

- Display Name.
- License Number.
- Address.

Dropdown sources:

- Active Legal Entities, with historical inactive values retained for existing rows.
- Daycare lifecycle statuses.

## Sync Behavior

- New row without `database_id`: proposed insert.
- Existing row with current `row_version`: proposed update.
- Older row version: conflict; no silent overwrite.
- Clearing a used row does not delete it.
- Lifecycle change is synchronized and audited.

## Audit Requirements

Record field changes, source spreadsheet/tab/row, sync batch, prior values, accepted values, actor, and timestamp.

## Bulk Edit Support

Allowed for editable fields. Every row is independently validated. One invalid row does not block valid rows.

## Open Questions

- Exact license number requiredness and format.
- Whether current Legal Entity should be materialized directly in `daycares` in addition to assignment history. The current recommendation is yes for usability, with history as the authority for historical ownership.
